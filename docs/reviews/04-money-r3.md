### P1 — An inquiry that escalates after the platform refunds it is dropped as "already recorded"; nobody is told and the chargeback is lost by default
**Where:** `src/utils/disputeOutcome.ts:48-58` (`selectDisputeOpenAction`), `src/app/api/webhooks/stripe/route.ts:524-525` (the `already_recorded` break), `:551-581` (inquiry branch stores the same `dispute_id`), `src/app/api/admin/orders/[id]/refund/route.ts:41-46, 61-73` (settle is allowed during an inquiry and is always a partial refund), `src/utils/reconcileStripe.ts:111-116` (the cron excludes this case), `src/utils/disputeOutcome.test.ts:68-69` (pins the swallowing).
**What happens:** A Discover or Amex inquiry lands on a paid order. The inquiry branch records `dispute_id`, leaves the status alone and tells admins to "respond in the Stripe dashboard before its deadline". The admin does what Stripe's own inquiry guidance and the runbook's refund flow both lead to: the artist approves and the admin settles, or the admin refunds from the app to make the inquiry go away. The settle route permits it (status is `paid`, not `disputed`) and issues its usual partial refund — price, shipping and their tax, fee retained. Stripe's dispute documentation, fetched today: "Inquiries on partially refunded charges can still escalate to a chargeback." The escalation arrives as `charge.dispute.updated` with status `needs_response` and the same dispute id. `selectDisputeOpenAction` walks: not a closed status, not an inquiry, order not `disputed`, `stripe_refund_id` set → `order.dispute_id === dispute.id` → `already_recorded`. The handler breaks with 200. No admin notification, no artist notification, no Sentry line. The daily reconcile cannot catch it either: its open-dispute branch deliberately skips a row that is `refunded` when Stripe also shows a refund. The response deadline passes; Stripe: "If you don't respond before the deadline, you automatically lose the dispute." `charge.dispute.closed` (`lost`) then runs cleanly — `stripe_reversal_id` is set so nothing is reversed, the order stays `refunded`, the artist is told "your payout for this order had already been returned". The buyer holds both the refund and the full chargeback amount; the platform is out the disputed amount plus the dispute fee, and the only thing that could have prevented it was the Stripe dispute email being read by hand.
**Why it's real:** The `post_refund` branch's `already_recorded` exit exists to absorb a redelivered `created` on an already-refunded order, and it keys on the dispute id alone. The R2 inquiry branch stores that same id before any refund. Nothing on the row distinguishes "we recorded this id as an inquiry" from "we recorded this id as a post-refund chargeback", so the escalation — the one event on which the admin must act — is indistinguishable from a duplicate. The unit suite pins exactly this input (`status: 'refunded', dispute_id: DISPUTE_ID`, `needs_response`) as `already_recorded`. Before R2 an inquiry froze the order (the first pass's P1), which was wrong in a different way but never silent. The same thing happens if the inquiry is answered with a full dashboard refund that `charge.refunded` reconciles to `refunded`, should the issuer escalate anyway.
**Fix direction:** Record what the stored dispute id meant — persist the last dispute status seen (`dispute_status` column, or a boolean `dispute_is_inquiry`) so the post-refund branch treats "recorded as an inquiry, now `needs_response`" as a new chargeback to notify on, exactly as the live-order branch already does for an escalated inquiry. Cheaper alternative: on the post-refund path, notify admins whenever the incoming status is a non-inquiry open status regardless of id match — a duplicate admin ping costs nothing next to a lost dispute. Have the reconcile cron report an open non-inquiry dispute on a refunded order when the row's recorded dispute state is an inquiry.

### P2 — An artist can put a listing with a live order back on sale; every buyer who then pays is refunded at the platform's expense, and neither they nor the artist is told
**Where:** `src/app/(artist)/listings/[id]/edit/page.tsx:246-251` (Status select always offers Available), `src/app/api/listings/[id]/route.ts:46-60` (`status` allowlisted, no orders check), `src/app/api/payments/checkout/route.ts:46` (only `status !== 'available'`), `src/app/api/webhooks/stripe/route.ts:359-385` (oversell branch: refund, audit row, Sentry warning, nothing else), `supabase/migrations/00055_disputed_holds_listing_slot.sql:1-27`.
**What happens:** A piece sells and the listing becomes `sold`. The artist opens Edit to fix a typo, or believes the sale fell through, and saves with Status set to Available — the select's first option, one click from the current "Sold". The PATCH route checks only ownership and writes `available`. The piece is back in the feed with a `paid` order holding `orders_one_live_per_listing`. A second collector checks out and pays; the buyer is charged, the artist transfer is created, the webhook insert hits 23505, the same-payment lookup finds nothing, and the oversell branch refunds them in full with `reverse_transfer`. The buyer lands on `/orders?success=true`, reads "Your purchase was successful!", and after the 60-second poll sees a row that says Refunded, with no email, no notification and no explanation. The artist sees nothing; admins see nothing (Sentry warning only). Stripe keeps the processing fee on every refund, and the Stripe Tax fee, so each repeat costs the platform roughly 3% of the total plus 80¢; the listing stays `available`, so the next collector repeats it until someone reads Sentry.
**Why it's real:** The second pass filed this as its last P3 with two fix directions; R13 took the index half (00055's own header says so). That makes the collision *safe*, not *absent*. I grepped every trigger on `listings` (search vector, alert stamps, follower notification, price drop) — none consults `orders` — and the PATCH allowlist admits `status` without a lookup. Only DELETE checks for an order (the 23503 branch). The oversold-buyer silence was already in the r2 appendix and is unchanged; here it is the consequence, not the claim.
**Fix direction:** In the listing PATCH, refuse a status change off `sold` while any order in `paid`/`shipped`/`delivered`/`disputed` references the listing (409 with "this piece has a live order — it goes back on sale when that order is refunded"), and hide Available in the edit form when `isSold`. Separately, give the oversell branch a buyer email and notification ("the piece was sold moments before your payment; you have been refunded in full") and an admin notification, since the only signal today is a Sentry warning.

### P2 — A second dispute on the same payment is treated as a redelivery of the first: nothing is reversed and nobody learns it closed
**Where:** `src/utils/disputeOutcome.ts:126-127` (`noop` keys on `dispute_outcome === 'lost'`, not on the dispute id), `src/app/api/webhooks/stripe/route.ts:583-605` (the second `created` lands in `post_refund` and overwrites `dispute_id`), `:728` (`noop` breaks before the notifications).
**What happens:** A buyer disputes $60 of a $400 order (a damaged frame — a "partial dispute" in Stripe's table of disputed amounts). The order is ineligible; the dispute is lost; the lost branch reverses $60 of the $340 payout and writes `status: 'refunded', dispute_outcome: 'lost'`. Weeks later the same buyer files a second dispute for the rest — Stripe: "you might receive more than one dispute per payment... a new dispute with a different reason code... or simply because the issuer acquired new information." `charge.dispute.created` for the new id finds `status: 'refunded'` → `post_refund`: `dispute_id` is overwritten with the new id and admins are told "the money already went back — respond with the refund as evidence", which is false ($60 went back). When the second dispute is lost, `selectDisputeCloseOutcome` sees `dispute_outcome === 'lost'` and returns `noop`: the remaining $280 of an ineligible artist's payout is never reversed, the platform absorbs it against its own policy, and the handler breaks before building any notification, so neither the artist nor the admins hear that the second dispute closed. The reconcile cron reads "dispute lost, order refunded" as consistent.
**Why it's real:** The row has one `dispute_id` and one `dispute_outcome`; the noop test at `disputeOutcome.test.ts:228-231` pins "lost redelivery is a no-op" on the outcome column alone, and no test constructs a second id. The reconcile route already assumes several disputes per payment ("newest first, so [0] is the live one"), so the model is known to the codebase. Stripe calls multiple disputes "extremely rare", which is why this is P2 and not higher; a partial first dispute also labels the whole order `refunded` while the buyer keeps the piece, which is display-only and not the claim here.
**Fix direction:** Make the redelivery check `dispute_id === dispute.id && dispute_outcome === 'lost'`; for a different id, run the lost branch with `reverseCents` capped at the payout minus `transfer.amount_reversed` (already retrieved in that branch). Let `post_refund` say "a refund of N¢ exists on this payment" rather than "the money already went back". A small `order_disputes` table (id, status, amount, outcome) is the durable fix if this ever needs to be exact.

### P3 — Three evidence columns stay artist-writable at every status, including `disputed`
**Where:** `supabase/migrations/00050_dispute_lifecycle_and_order_guard.sql:39-69` (freeze list omits `shipping_address`, `tracking_number`, `carrier`), `supabase/migrations/00002_missing_tables_and_policies.sql:195-196` (UPDATE policy is owner-only, no status clause; no column grants on `orders` anywhere), `src/utils/evaluateProtection.ts:116-122`, `docs/SELLER_PROTECTION_SPEC.md:23` ("delivered to the address on the Custom Canvas order").
**What happens:** A chargeback freezes a shipped order and its protection verdict. The admin gathers evidence per the runbook from the row: tracking number, carrier, ship-to address. The artist, with their own session against the PostgREST endpoint (the same call `services/orders.ts` makes), sends `{ tracking_number, carrier, shipping_address }` for the disputed order. The status is unchanged, so the guard's transition check does not fire; the three columns are not copied from OLD; RLS passes on ownership. The row now says whatever the artist wants it to say: a different address than the buyer gave (which is also what the buyer's Orders page renders as "Ships to"), a tracking number that resolves. Money does not move on it — `protection_status` was frozen at dispute time — but the evidence the platform submits under its own name is editable by the party it is evidence against, after the dispute exists. The address in particular has no legitimate artist edit at all: the Studio never writes it.
**Why it's real:** 00040's own comment states the principle ("letting an artist self-attest... would let them shift their own losses") and froze `shipped_at`, `signature_confirmed` and the snapshot columns for exactly this reason; the three columns above are the remaining evidence inputs and were never added. Stripe holds the taxed address on the session, so truth is recoverable, which is why this is P3. The tracking and carrier edits are legitimate before shipping (typo fixes), so the fix is a status gate, not a blanket freeze.
**Fix direction:** In `guard_orders_update`, always copy `shipping_address` from OLD for non-privileged writers, and copy `tracking_number`/`carrier` from OLD when `OLD.status IN ('delivered','disputed','refunded')`. Add the three rows to the db-smoke transition matrix.

### P3 — A dispute won on a delivered order re-stamps `delivered_at` to the day the dispute closed
**Where:** `supabase/migrations/00022_review_fixes_phase79.sql:6-17` (`set_order_delivered_at`: fires on any transition into `delivered`, no null guard, no privilege check), `src/app/api/webhooks/stripe/route.ts:833-843` (restore writes `status: outcome.status` from `disputed`), `scripts/db-smoke.sql:594-599` (pins that the trigger fires under the service role), contrast `00050:71-77` (`shipped_at` is only stamped when null).
**What happens:** A piece is delivered on 1 August (`delivered_at` 1 Aug). A chargeback lands on 20 August; the order freezes with `pre_dispute_status: 'delivered'`. On 5 October the issuer rules for the artist; the restore sets `status: 'delivered'`; the trigger sees `OLD.status = 'disputed'` and stamps `delivered_at := now()`. The order now records delivery two months after shipping. `delivered_at` is requirement-3 evidence, the date any future evidence pack quotes, and — if Stripe's "refile with new information" second dispute arrives — the timestamp `assessProtection` would carry. Nothing user-facing reads it today (the review-reminder cron keys on `updated_at`; both order pages show `created_at`), which is why this is P3: it is the next reader of `delivered_at` that gets the wrong answer.
**Why it's real:** R3 added the null guard to `shipped_at` for this exact reason ("a restored order re-marked shipped keeps its original evidence") but only inside the `NOT is_privileged()` branch, and `delivered_at` is stamped by a different, older trigger that predates the dispute lifecycle. The restore is a privileged write, so nothing guards it.
**Fix direction:** Add `AND OLD.delivered_at IS NULL` to the trigger condition and pin it in db-smoke's transition matrix (privileged `disputed → delivered` with a prior stamp keeps the stamp). One line plus one assertion.

### P3 — A resent or late dispute *open* event re-freezes a restored order; the runbook says resending is safe
**Where:** `src/utils/disputeOutcome.ts:42-58` (the closed-status guard reads the event payload), `src/app/api/webhooks/stripe/route.ts:511` (open handler does not select `dispute_outcome`), `:617-637` (freeze), `docs/runbook.md:14-18` ("Replaying is safe").
**What happens:** Stripe's Event reference, fetched today: "The contents of `data` never change." A `charge.dispute.created` event therefore carries `needs_response` forever, however late it is delivered or resent. A chargeback on a shipped order is won; the order is restored to `shipped` with `dispute_id` kept and `dispute_outcome: 'won'`. An operator clearing the endpoint's failure list resends that dispute's `created` (or a `charge.dispute.updated` from the evidence-submission day) as runbook step 1 instructs. `selectDisputeOpenAction`: `needs_response` is not a closed status, not an inquiry, the order is not `disputed`, no refund → `chargeback`. Protection is re-assessed against today, `protection_status` is overwritten, the order becomes `disputed` with `pre_dispute_status: 'shipped'`, and the artist receives a second "Payment disputed — send evidence right away" notification for a dispute they won. No `closed` will ever follow. The next day's reconcile flags `dispute_closed_order_still_disputed` (it sweeps every disputed row), and resending `closed` heals it (the restore CAS on `disputed` passes, `pre_dispute_status` is `shipped`). Net: a day of a wrongly frozen order, a spurious protection re-verdict written over the original, and a scary notification, on an action the runbook calls safe.
**Why it's real:** R13's `isClosedDisputeStatus(dispute.status)` guard, added for the second pass's P2, can only see the payload, and the payload of an open event is always open. The fact that would settle it — `dispute_outcome` is already `'won'` for this `dispute_id` — sits on the row and is not read by the open handler. The Stripe retry schedule (up to three days) cannot span a won dispute (two to three months), so in practice this is the operator path plus the retried-inquiry variant (a `created` for an inquiry retried after its `warning_closed` arrives lands as a fresh "Bank inquiry" notification after the inquiry closed).
**Fix direction:** Select `dispute_outcome` in the open handler and return `already_recorded` when `dispute_id === dispute.id && dispute_outcome !== null`. Amend the runbook: dispute open events must not be resent once the dispute is closed; resend `closed` instead.

## Not findings

- Duplicate `checkout.session.completed`: payment-intent pre-check, `orders_payment_intent_unique`, the 23505 same-payment branch, and `resumeIfIncomplete` gated on the order still being `paid` converge; a concurrent duplicate blocks on the unique index until the first commits.
- Out-of-order `charge.refunded` / `charge.dispute.*` before the order exists: 409 and Stripe retries; oversell audit rows count as a match; a failed read is now a 500 rather than a 409.
- `charge.dispute.closed` before `created`: the `needs_assessment` path assesses, CAS-persists on `pending`, re-reads and re-selects; a concurrent freeze is tolerated; the late `created` with a closed-status payload is `already_recorded`, and with an open payload on a `refunded` row lands in `post_refund` (harmless; status untouched).
- Won/inquiry-closed restore: refund evidence outranks `pre_dispute_status`; the write is CAS on `disputed`; `dispute_id` survives so a replay of a *closed-status* payload is recognised (the open-payload replay is the P3 above).
- Lost branch: reversal is `min(dispute.amount, artist_payout_cents)`, idempotency-keyed on the dispute id, skipped when `stripe_reversal_id` is set or the transfer is already fully reversed at Stripe; a protected order is absorbed; a transient evidence read is a retry, not an `ineligible` verdict.
- Chargeback after a settled refund (different dispute id or first dispute): `post_refund` records and notifies; lost then reverses nothing because the reversal exists.
- Refund settled during an open chargeback: refused by the settle route (409) and hidden in the admin page; a refund settled between the ruling and the `closed` delivery is honoured by the restore's CAS.
- Reconcile cron: 7-day payment window for `no_order`, plus refunds and disputes created in the window, plus every `disputed` row regardless of age — the window regression from r2 is closed; alerts batch to admins and Sentry.
- Payout math: `calcSplit` is exactly the locked rule (commission = round(15% of price), payout = price − commission + shipping, fee = ceil((2.9% × (price + shipping) + 30¢) / 0.971)); the three `DECISIONS.md` examples reproduce; `transfer_data.amount` equals the recorded payout; float rounding never disagrees with integer half-up for any price up to $100,000; conservation holds by construction.
- Refund math: `calculateRefundSplit` returns price + shipping + their proportional tax; fee and fee tax retained; the settle refund is always partial (fee ≥ 31¢), so `charge.refunded` never double-handles it; Stripe Tax's proportional reversal on a uniform-rate basket yields the same tax figure to the cent.
- Checkout while the listing is edited: every amount and the evidence snapshot are locked in session metadata; `buildOrderRecord` never reads the live row; a listing hidden mid-checkout still becomes `sold`. Sold to someone else mid-checkout: index plus idempotency-keyed full refund with `reverse_transfer` (the artist-driven relist that makes it repeatable is the P2 above).
- Order state machine, non-privileged: only `paid|shipped → shipped`; `delivered` only through `mark-delivered` (CAS on `shipped`); `delivered_at`, `shipped_at`, `pre_dispute_status`, `shipped_email_sent_at`, every money, party and evidence-snapshot column frozen; buyers have no UPDATE policy; INSERT policy dropped. No client sequence reaches or leaves `refunded`/`disputed`.
- `confirm-pickup`: per-party atomic stamp, both-confirmed promotion with self-heal, refuses `disputed` and refund-in-flight; a promotion that loses to a concurrent freeze fails closed and the frozen verdict stands. `approve-refund`: artist-only, CAS on null, refuses non-open statuses. `notify-shipped`: once-only claim. `mark-delivered`: ownership plus CAS.
- Commission state machine: `pending → quoted → in_progress → delivered → confirmed`, `pending|quoted → cancelled`, `in_progress|delivered → disputed → (withdraw) pre-status | (admin) confirmed|cancelled`. Every route ownership-checks and CASes on the read status; both zod schemas carry no `status` or id fields; no client UPDATE policy; `updates` refuses closed states; no money moves.
- `stripe-connect`: idempotency key per artist row, row write asserted, account deliberately kept on a failed write; `account.updated` requires `payouts_enabled` and active `transfers` and is written unconditionally so a downgrade flips it off.
- Account deletion: refused while party to `paid`/`shipped`/`disputed` or an approved-but-unsettled refund; money rows outlive their parties; both dispute handlers tolerate a null artist (loudly).
- `is_privileged()`: service role, no-JWT, admin session; the webhook and every route write as the service role; the guard's transition branch is the client boundary.
- Stripe API version `2026-02-25.clover` with stripe@20: `collected_information.shipping_details` and `total_details.amount_tax` ride the session payload, so the taxed ship-to address is what is recorded.
- Settled decisions left alone: destination charges, Express accounts, fee pass-through and its uncovered components, the payments gate, pickup tax sourcing (D2), artist delivery attestation (D1), commission dispute exits (D5), the 14-day payout delay covering refunds after payout.
