### P1 — `charge.dispute.closed` processed before (or concurrently with) `charge.dispute.created` reverses a Protected artist's payout, because protection is only ever assessed by the created handler
**Where:** `src/app/api/webhooks/stripe/route.ts:659-701` (the lost branch), `src/utils/disputeOutcome.ts:106-116` (`platformAbsorbs = protection_status === 'protected'`), `route.ts:588-607` (the only assessment site), `supabase/migrations/00040_seller_protection.sql:24` (`protection_status` defaults to `'pending'`).
**What happens:** An artist ships a $400 piece with USPS tracking on day two, marks it delivered, replies to every message; the listing had four photos and long notes. The buyer's Discover card raises an inquiry. The inquiry path records `dispute_id` and — correctly — does not assess protection. Nobody answers the inquiry in Stripe (the admin notification only says "respond before its deadline"). Stripe's dispute documentation states that an unanswered Discover inquiry becomes an unchallengeable chargeback which Stripe "immediately closes as lost as soon as we notify you": the escalation (`charge.dispute.updated`, status `needs_response`) and `charge.dispute.closed` (status `lost`) are generated in the same instant, and Stripe does not order deliveries. If `closed` lands first, or the two are processed concurrently, the lost branch reads `protection_status = 'pending'`, `dispute_outcome = null`, `stripe_reversal_id = null`. `platformAbsorbs` is false because `'pending' !== 'protected'`, so it reverses `min(dispute.amount, artist_payout_cents)` — the artist's whole $340 — sets `refunded` / `lost`, and tells the artist "$340.00 was deducted from your payout, as this order was not Protected". The `updated` event then arrives, finds `status = 'refunded'` with `dispute_id` already equal (from the inquiry), returns `already_recorded`, and no assessment ever runs. The artist met all six requirements and the platform's own policy says it absorbs this loss. In the concurrent variant without an inquiry the freeze still commits (its CAS is `status <> 'disputed'`), so the row ends up `protection_status = 'protected'`, `dispute_outcome = 'lost'`, payout reversed — contradicting itself.
**Why it's real:** The lost branch has no notion of "not yet assessed": `selectDisputeCloseOutcome` treats anything but `'protected'` as ineligible, and `'pending'` is the default every order carries until the created handler writes over it. The 409 retry on `!order` protects only against the order not existing, not against the dispute not having been opened on it. Stripe's inquiry and unchallengeable-dispute behaviour is quoted from its documentation, fetched today; Discover is a mainstream US card and the platform is Houston-only. The R2 unit suite pins every lost/won case with the order already frozen; none starts from `pending`.
**Fix direction:** In the closed handler, if the row shows no processed open event for this dispute (`protection_status = 'pending'` and `dispute_id <> dispute.id`, or `pre_dispute_status` null on a non-inquiry), either run `assessProtection` there before deciding or return 409 so Stripe redelivers after `created` has been processed. `selectDisputeCloseOutcome` should refuse to reverse when `protection_status` is `'pending'`.

### P2 — A late or resent `charge.dispute.created`/`updated` after a won or closed-inquiry restore re-freezes the order as `disputed`, with no closing event ever coming
**Where:** `src/app/api/webhooks/stripe/route.ts:480-506, 596-612` (open handler), `:735-743` (restore nulls `dispute_id`), `src/utils/disputeOutcome.ts:37-46` (no closed-status check).
**What happens:** A chargeback is frozen on a shipped order. Weeks later the issuer rules for the artist; `closed` (`won`) restores `shipped`, clears `dispute_id` and `pre_dispute_status`. Then an open event for the same dispute arrives late: a `charge.dispute.updated` that 409'd earlier because its `orders` read hit a transient error (`.maybeSingle()` returns `data: null` on an error, and the code treats null as "no order yet") and is now on Stripe's multi-day retry schedule; or an operator following runbook step 1 ("click the event → Resend. Replaying is safe") replays the `created` event while tidying up a failure list. `selectDisputeOpenAction` sees a non-`warning_` status, a non-`disputed` status, no refund, and `dispute_id === null`, so it returns `chargeback`: protection is re-assessed against today's evidence, the order becomes `disputed` with `pre_dispute_status = 'shipped'`, the artist gets a second "Payment disputed" notification. No `closed` will ever follow. From `disputed` nothing in the app moves the order (guard: only `paid`/`shipped` may change; `mark-delivered`, `confirm-pickup`, `approve-refund` all refuse it; the admin page has no status control), and the reconcile cron will not see it because the payment is months outside its window (next finding). The same happens if Stripe also emits `charge.dispute.updated` with status `won` alongside `closed` and it is processed second.
**Why it's real:** The open handler never inspects the dispute's status for `won`/`lost`/`warning_closed`, and the restore branch discards the only fact (`dispute_id`) that would let `already_recorded` catch a replay. The lost branch, by contrast, keeps `dispute_id`, so a replay after a loss is harmless — the asymmetry is the bug. UNVERIFIED: whether Stripe emits `charge.dispute.updated` at closure (its reference says "usually with evidence"); the staging dispute verified end to end has an event list in the Stripe dashboard — if an `updated` with status `lost` sits next to its `closed`, this finding is normal-flow and P1. Either way the retry and resend paths above stand.
**Fix direction:** Treat a dispute whose status is `won`, `lost` or `warning_closed` as `already_recorded` in `selectDisputeOpenAction`, and keep `dispute_id` (or a `last_dispute_id`) through the restore so a replay of the same dispute is recognised. Separately, distinguish a failed read from a missing row before answering 409.

### P2 — The won/inquiry-closed restore overwrites a refund settled between the ruling and the event's delivery, because `pre_dispute_status` outranks refund evidence and the write has no compare-and-swap
**Where:** `src/utils/disputeOutcome.ts:99-104` (`restoredStatus` priority), `src/app/api/webhooks/stripe/route.ts:735-747` (`.eq('id')` only), `src/app/api/admin/orders/[id]/refund/route.ts:37` (refuses only `refunded`), `src/app/admin/orders/page.tsx:166` (Settle shows whenever `refund_approved_at && status !== 'refunded'`).
**What happens:** The artist approved a refund on a `paid` order; before the admin settled it the buyer's bank filed a chargeback, freezing the order with `pre_dispute_status = 'paid'`. Stripe forbids refunds while the dispute is open. The issuer rules for the platform. The first `closed` delivery fails on a transient DB error (any of the restore's write paths returns 500) and goes onto Stripe's retry schedule. The admin, who has Stripe's "dispute won" email, opens `/admin/orders`, sees "Settle refund" still offered, and settles: refund and reversal succeed (the dispute is closed), `stripe_refund_id` and `stripe_reversal_id` are written, status becomes `refunded`, the listing is relisted. The retried `closed` then runs `restoredStatus`: `pre_dispute_status` is `'paid'`, so it returns `paid` before ever looking at `stripe_refund_id`, and the update — filtered on id alone — writes `status: 'paid'`. The buyer's Orders page shows Paid for money they have back; the artist's Sales tab offers "Mark as Shipped" and "Approve refund" on it; the admin totals count it as revenue; the relisted piece is `available` while a `paid` order holds its one-live-order slot, so the next buyer of it is auto-refunded as an oversell. This is the first pass's second P1 reached through the column that was added to fix it.
**Why it's real:** The unit test "won after a settled refund restores to refunded, not paid" passes only because it constructs the order with `pre_dispute_status: null`; with the value the created handler always writes, the function returns the saved status. The restore write has no `.eq('status', 'disputed')`, unlike the freeze, so it cannot notice the row moved underneath it.
**Fix direction:** Check `stripe_refund_id` / `status === 'refunded'` before `pre_dispute_status` in `restoredStatus`, and give the restore update a compare-and-swap on `status = 'disputed'` (treat zero rows as already-handled, not a retry). Hiding Settle on `disputed` orders is a small third step.

### P2 — The reconcile cron only inspects payments created in the last seven days, so the refunds and disputes it exists to catch — which land weeks to months after payment — are never in its window
**Where:** `src/app/api/cron/stripe-reconcile/route.ts:8, 25-35` (`paymentIntents.list({ created: { gte: now − 7d } })`), `docs/runbook.md:37-44` ("the safety net").
**What happens:** A buyer receives a piece, keeps it a fortnight, and the admin refunds the order from the Stripe dashboard on day 20 with the transfer-reversal box ticked — while the webhook secret has just been rotated, so every event 400s. The buyer has the money, the artist's balance was debited, and the order stays `delivered`: the artist's totals count the payout, both Orders pages show Delivered, and if the admin is asked later they will settle it again through the app (Stripe refuses, but only after a confusing 502). The cron runs every day and never lists that payment because it is 20 days old. Same for a dropped `charge.dispute.closed`: chargebacks are decided two to three months after payment per Stripe's documentation, so `dispute_lost_order_not_refunded` and `dispute_closed_order_still_disputed` — both implemented and tested in `reconcileStripe.ts` — can in practice never fire from this route. The 7-day window catches exactly one thing: a payment with no order.
**Why it's real:** The window is applied to `payment_intent.created`, not to when the refund or dispute happened. Nothing else lists Stripe refunds or disputes: I grepped `src/` and `scripts/` for `refunds.list`, `disputes.list` (only the per-PI lookup inside this route), and `events.list`. The runbook's acceptance test — a dashboard refund with the secret deliberately wrong — was necessarily on a fresh payment.
**Fix direction:** Add two more listings keyed by event time — `refunds.list({ created: { gte } })` and `disputes.list({ created: { gte } })`, plus a pass over every `orders` row currently `disputed` regardless of age — and feed their payment intents through the same diff. The PI window can stay for the no-order check.

### P2 — A transient failure reading the order's evidence at dispute time is frozen as an `ineligible` verdict, and the artist's payout is reversed on it
**Where:** `src/app/api/webhooks/stripe/route.ts:71-77` (`assessProtection` returns null when the `.single()` read fails), `:593-594` (`assessment?.status ?? 'ineligible'`), `:596-607` (frozen in the same write), `supabase/migrations/00050:60` (`protection_status` frozen for non-privileged writers).
**What happens:** A chargeback arrives on a fully compliant shipped order. The freeze path first re-reads the order for its evidence columns; that read hits a Supabase connection reset or statement timeout (the row exists — it was read three statements earlier — so only a transient error can produce null here). `assessment` is null, `protectionStatus` becomes `'ineligible'`, and the freeze write succeeds, so the event is acked with 200 and never retried. The artist is told "This order was not Protected, so the amount will be deducted from your payout. Reasons: " with an empty list. Months later the dispute is lost; the lost branch reads `'ineligible'` and reverses the payout. Nothing re-assesses: the column is frozen for everyone but the service role, the created event will not redeliver, and the Studio badge computes its own optimistic view, so the artist sees "Protected" in Studio and "not Protected" in the notification.
**Why it's real:** Every other failure in this handler returns `retryLater`; this one is coerced into the worst-case verdict. `artistRepliedInTimeForOrder` deliberately degrades in the lenient direction on read failure ("Read failures degrade to 'replied'"); the outer read degrades in the strict direction with no comment saying so.
**Fix direction:** `if (!assessment) return retryLater('Protection evidence read failed')` — Stripe redelivers and the assessment runs against the same frozen evidence. One line.

### P3 — The redelivery resume path treats "listing available" as "post-insert steps never ran", which is also what a settled refund or a manual relist looks like
**Where:** `src/app/api/webhooks/stripe/route.ts:270-289` (`resumeIfIncomplete`), `:296-299, 348-351` (both callers), `docs/runbook.md:14-18` ("Replaying is safe: order creation dedupes on the payment-intent id").
**What happens:** A sale completes normally. Later the refund is settled and the piece relisted (or a chargeback is lost and, per the runbook, the artist relists by hand). An operator working through a webhook failure list per runbook step 1 or 4 resends this session's `checkout.session.completed` — the runbook says replaying is safe. The handler finds the existing order, sees the listing `available`, logs "Resuming post-insert steps", and runs `completeSale`: the listing is set to `sold` with the original `sold_price_cents` and no live order holding it, the buyer gets a fresh "order confirmation" for a purchase they were refunded, the artist gets a second "New sale" email and in-app notification, and a pickup order posts another "ready to coordinate" system message in the thread. The piece is off the market until someone notices; the emails cannot be recalled.
**Why it's real:** The idempotency key is the listing's status, and two legitimate paths (`charge.refunded` relist, admin settle relist, manual relist) reset it after completion. The order row carries the fact that matters — it is no longer `paid` — and the resume never looks at it.
**Fix direction:** Resume only when the order is still `paid` (read `status` alongside `id` in both lookups). A `sale_completed_at` stamp would be the exact check if that ever needs to survive a status change.

### P3 — The admin settle route's close and relist writes are unchecked, so a failed close reports "Refund settled" over a `paid` order that Stripe has already refunded
**Where:** `src/app/api/admin/orders/[id]/refund/route.ts:98` (`update({ status: 'refunded' })` with no result read), `:111-115` (relist likewise), `src/app/admin/orders/page.tsx:85-86` (optimistic flip to `refunded` on `res.ok`).
**What happens:** Refund and reversal succeed and their ids are persisted. The status update fails (connection drop, or a future guard/trigger raising) — the error is discarded and the route returns `ok: true`. The admin sees "Refund settled." and the row flip to Refunded until reload; the row is actually `paid` with `stripe_refund_id` and `stripe_reversal_id` set. The artist's Sales tab still offers Mark as Shipped and counts the payout in totals; the buyer's page says Paid. Recovery is by accident: after a reload the Settle button is back (`refund_approved_at` set, status not refunded) and a second click skips both Stripe calls and rewrites the status — if the admin thinks to click it. The reconcile cron flags `stripe_refunded_order_not_refunded` only if the order is under seven days old (see the P2 above).
**Why it's real:** R2 item 6 made every `orders`/`listings` status write in the webhook check its result and return non-2xx; this route was not in that item and still discards both results. The convention's rule 1 is written for client writes, but its reason ("silence is what this rule bans") applies verbatim.
**Fix direction:** Read `{ data, error }` from the close with `.select('id').maybeSingle()`; on error return 502 with "Refund done at Stripe but the order could not be closed — retry" (the retry is already idempotent). Same for the relist.

### P3 — A `disputed` order does not hold the one-live-order slot, the artist can relist the piece, and the eventual won-restore then collides with the second sale and loops
**Where:** `supabase/migrations/00010_order_oversell_guard.sql:4-6` (index covers `paid`,`shipped`,`delivered` only), `src/app/(artist)/listings/[id]/edit/page.tsx:246-249` (Status select offers Available on a sold listing), `src/app/api/listings/[id]/route.ts:47-58` (`status` is allowlisted with no order check), `src/app/api/webhooks/stripe/route.ts:735-747`.
**What happens:** A buyer pays with a stolen card; the fraud chargeback lands three days later on the unshipped order (`disputed`). The artist, reasonably, edits the sold listing back to Available and a second collector buys it — the insert succeeds because the disputed order is not in the partial index — ships it, and is paid. Ten weeks later the first dispute is, unusually, won. The restore tries to set order A to `paid`, which now violates `orders_one_live_per_listing` (order B is `paid`/`shipped`); `restoreError` returns 500, Stripe retries for three days and gives up, and order A is `disputed` forever with `dispute_id` set. The reconcile cron cannot see it (payment is ten weeks old). Had the dispute been lost — the common outcome — the row closes cleanly, which is why this is P3.
**Why it's real:** The edit form and PATCH route were read; neither consults `orders`. Only the DELETE path checks for an order (the 23503 branch). `disputed` is absent from both the index and the relist count in the refund paths, consistently — but the restore path assumes the slot is free.
**Fix direction:** Add `disputed` to the partial index (a disputed order still occupies the piece; the freeze update is the same row so it cannot self-collide), or refuse `sold → available` in the listing PATCH while any `paid`/`shipped`/`delivered`/`disputed` order references the listing.

## Not findings

- Webhook idempotency on `checkout.session.completed`: payment-intent pre-check, `orders_payment_intent_unique`, and the 23505 same-payment branch converge; a duplicate arriving after `completeSale` finds the listing `sold` and stops.
- Out-of-order `charge.refunded`/`charge.dispute.*` before the order exists: 409 and Stripe retries; oversell audit rows count as a match.
- Inquiry lifecycle (`warning_*` → `warning_closed`, or escalation via `updated`): branch selection is correct and tested; status is left alone, protection not assessed, restore lands on the right status through the fallbacks.
- Chargeback after a settled refund: `post_refund` records the id and leaves `refunded` alone; a lost outcome then reverses nothing because `stripe_reversal_id` is set.
- Partial chargebacks: reversal is `min(dispute.amount, artist_payout_cents)`, idempotency-keyed on the dispute id.
- Refund after payout: the reversal pulls from the connected balance; the 14-day payout delay covers it; the settle route's step order and persisted ids make retries resume from the failed step.
- Payout math: `calcSplit` is exactly the locked rule (commission = round(15% of price), payout = price − commission + shipping, fee = ceil((2.9% × (price + shipping) + 30¢) / 0.971)); `transfer_data.amount` equals the recorded payout; float rounding never disagrees with integer arithmetic for any price up to $2,000; conservation holds by construction.
- Refund math: `calculateRefundSplit` returns price + shipping + their proportional tax; fee and fee-tax retained; `Math.round` once; all 84 money tests green.
- Checkout while the listing is edited: every amount and the evidence snapshot are locked in session metadata; `buildOrderRecord` never reads the live row. Listing deleted mid-checkout: loud 500 plus Sentry, by design. Sold to someone else mid-checkout: unique index plus idempotency-keyed full refund with `reverse_transfer`.
- Order state machine (artist/buyer-drivable): guard allows only `paid`/`shipped` → `shipped` for non-privileged writers; `delivered` is server-CAS'd from `shipped`; `delivered_at`, `shipped_at`, `pre_dispute_status`, `shipped_email_sent_at`, all money and evidence columns frozen; buyers have no UPDATE policy; INSERT policy dropped. No sequence reaches `refunded`/`disputed` or leaves them from the client.
- `confirm-pickup`: per-party atomic stamp, both-confirmed promotion with self-heal, refuses `disputed` and refund-in-flight. `approve-refund`: artist-only, CAS on null, refuses non-open statuses. `mark-delivered`: ownership check, CAS on `shipped`. `notify-shipped`: once-only claim.
- Commission state machine: `pending → quoted → in_progress → delivered → confirmed`, `pending|quoted → cancelled`, `in_progress|delivered → disputed → (withdraw) pre-status | (admin) confirmed|cancelled`. Every route ownership-checks and CASes on the read status; zod schemas cannot smuggle `status`; no client UPDATE policy; `updates` refuses closed states. `accepted`/`completed` exist in the type but no writer produces them — harmless.
- `stripe-connect`: idempotency key on `accounts.create`, row write asserted, account deliberately not deleted on a failed write; `account.updated` requires `payouts_enabled` and active `transfers`.
- Stripe API version `2026-02-25.clover` with stripe@20: `collected_information.shipping_details` and `total_details.amount_tax` are present on the session in the event payload, so the taxed ship-to address is what gets recorded.
- `services/orders.ts` `updateOrderStatus` `.select().single()` on `orders` (not a column-restricted table): zero rows throw and the caller toasts. Equivalent to the convention.
- Settled decisions left alone: destination charges, Express accounts, fee pass-through and its uncovered components, payments gate, pickup tax sourcing, artist delivery attestation (D1), commission dispute exits (D5).
