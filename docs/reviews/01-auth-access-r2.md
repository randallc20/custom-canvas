### P2 — The public storage buckets are listable with the anon key, so the approval gate hides the shop but not its images

**Where:** `supabase/migrations/00002_missing_tables_and_policies.sql:230` (`listing-images` SELECT `USING (bucket_id = 'listing-images')`), `:238` (avatars), `:248` (banners), `:264` (artist-photos), `:272` (artist-videos); `src/lib/signedUpload.ts:25` (object path is `<profile id>/<timestamp>-<random>`); contrast `00012_review_security_fixes.sql:46-61` (the one bucket whose SELECT is scoped).

**What happens:** An anonymous visitor holding the public anon key calls the storage list endpoint on `listing-images` (`supabase.storage.from('listing-images').list('')`). The five public buckets carry an unconditional `storage.objects` SELECT policy with no role restriction, and Supabase applies that policy to `list`/`search`, so the call returns every top-level folder, which is every uploader's profile id, and a second call per folder returns every object. Each path becomes a public URL. A draft, pending, or rejected artist's listing photos and personal photos are all readable and enumerable, even though 00033/00036 went to some length to make the listing, image, education, and personal-photo *rows* invisible for a non-live artist. The same listing pulls every avatar and banner on the platform keyed by profile id.

**Why it's real:** The policies are `USING (bucket_id = '…')` with nothing else, and nothing in a later migration drops or narrows them (00038 only touched the INSERT side of two buckets; the smoke test does not pin storage policies). Public buckets serve object GETs without any policy, so these SELECT policies exist only to permit listing and signed-URL creation, and no client code lists a bucket (grep for `.list(` on storage finds nothing). The 00038 commit message says the series leak mattered because it let anon "reconstruct the shop the approval gate exists to hide"; the images are the shop. **UNVERIFIED by execution:** I did not run the list call. What settles it: `curl -H "apikey: <anon>" -H "Authorization: Bearer <anon>" -X POST <url>/storage/v1/object/list/listing-images -d '{"prefix":"","limit":100}'` against staging. A JSON array of folders confirms it; a `[]` or 4xx kills the finding.

**Fix direction:** Drop the five unconditional SELECT policies on the public buckets (public-URL reads do not need them) and, if any future surface needs to list, add owner-folder policies shaped like `Users can delete own avatar`. Add the storage policy matrix to `db-smoke.sql` so the next bucket fails closed.

### P2 — Self-deletion during an open Stripe Checkout session orphans the payment: the webhook can never record the order

**Where:** `src/app/api/account/delete/route.ts:42-66` (refusal checks `orders` only, then `deleteUser`); `src/app/api/webhooks/stripe/route.ts:338-389` (order insert; a non-23505 error returns 500 for retry) and `:307-316` (listing gone → 500); line numbers as of the R13 commit `74750ae`, which landed mid-review and did not change this logic; `supabase/migrations/00049_orders_survive_account_delete.sql:27-30` (`orders.buyer_id` still `REFERENCES profiles(id)`, so the row must exist at insert time); `src/app/api/payments/checkout/route.ts:127-181` (session created with `buyer_id` in metadata; no expiry set, so Stripe's 24-hour default applies).

**What happens:** A buyer clicks Buy, lands on Stripe Checkout, and leaves the tab open. In another tab they delete their account. The delete route counts open orders, finds none (the order does not exist until payment), and deletes the auth user; `profiles` cascades. Any time in the next 24 hours they return to the Checkout tab and pay. Stripe charges the card and creates the destination transfer to the artist. `checkout.session.completed` builds the order record from metadata and inserts it; Postgres rejects the insert on `orders_buyer_id_fkey` because the profile is gone. The error code is 23503, not 23505, so the handler returns 500 and Stripe retries for three days, failing every time. `completeSale` never runs: the listing stays `available` (a second buyer can now buy it and take the oversell refund path), no confirmation or new-sale email goes out, and there is no `orders` row for a later refund, dispute, or the reconcile cron to attach to. The mirror case is an artist with an `available` listing who deletes their account while a buyer is mid-Checkout: the listing cascades away, the webhook hits the `!listing` branch and 500s forever, and the buyer has paid an artist who no longer exists on the platform while the transfer sits in an orphaned Connect account.

**Why it's real:** R1 deliberately scoped the refusal to existing orders and the FK to `SET NULL` on delete, which only helps once the row exists. The webhook's insert path distinguishes only 23505; every other error is a retry. `buildOrderRecord` takes `buyer_id` from session metadata with no existence check. The daily reconcile cron (`src/app/api/cron/stripe-reconcile/route.ts`) will report the payment-with-no-row mismatch, so the money is not silently lost, but nothing in the app can recover the order. At today's volume this is rare, which is why it is P2 and not P1.

**Fix direction:** In the webhook, treat a 23503 on `buyer_id` the way the schema already tolerates a deleted buyer: insert the order with `buyer_id: null` (and `listing_id: null` when the listing is gone, keeping the money columns and the payment intent), then `completeSale` skips the buyer email and alerts admins. Separately, the delete route could refuse when a Checkout session for this buyer or this artist's listings was created in the last 24 hours (a `checkout_sessions` stamp table, or a Stripe list call), but the webhook change is the one that closes the hole.

### P2 — Any chat participant can post platform-styled `system` messages and forged `quote_card`s

**Where:** `src/app/api/messages/route.ts:19-28` (`message_type` and `attachment` are passed to the insert verbatim); `supabase/migrations/00038_launch_hardening.sql:101-110` (the messages INSERT policy checks sender and membership only) and `00045_message_type_file.sql:8-9` (the CHECK allows `system` and `quote_card`); `00001_initial_schema.sql:322` (attachment CHECK allows `quote_card`) and `00015_phase6_review_fixes.sql:5-8` (attachment INSERT policy checks message ownership only); `src/components/chat/MessageBubble.tsx:39-41` (a `system` message renders as centred italic text with no sender, no avatar, no timestamp) and `:69-127` (a `quote_card` renders Accept/Decline for the non-sender with the price taken from attachment metadata).

**What happens:** A scammer registers as a buyer, opens a thread with an artist (any signed-in user can, by design), and POSTs to `/api/messages` with `message_type: "system"` and content "Custom Canvas: your payout failed verification. Re-enter your bank details at https://customcanvas-payouts.example within 24h." The route inserts it under the caller's session, the policy passes, and the artist's thread shows a notice visually identical to the real pickup-coordination notice the webhook posts (`webhooks/stripe/route.ts:163-168`, R13 numbering), with nothing to indicate who wrote it. The conversation preview shows the text too. The reverse works on buyers. The second shape: an artist on a real commission posts a `quote_card` whose attachment metadata says `quoted_price_cents: 10000` while the row's actual quote (set through `/api/commissions/[id]/accept`) is 100000; the buyer sees a $100 card with an Accept button, clicks it, and `/confirm` moves the commission to `in_progress` at the row's $1,000. No money moves in commissions, so this is deception rather than loss, but the card is the artefact the buyer acted on.

**Why it's real:** I tried to find the guard. `guard_messages_update` (00009) freezes `message_type` on UPDATE only; there is no BEFORE INSERT trigger on `messages` or `message_attachments`. The route has no allowlist and the client (`src/services/messages.ts:61-71`) sends whatever `message_type` it is given. The direct PostgREST path is open too, so a route-only fix is incomplete. The legitimate writers of `system` and `quote_card` (the webhook, `commissions/[id]/accept`, `commissions/[id]/updates`) all use the service-role client, so a DB guard keyed on `is_privileged()` would not break them.

**Fix direction:** Add a BEFORE INSERT guard on `messages` and `message_attachments` that, when not `is_privileged()`, rejects (or coerces to `text`) any type outside `text | image | file | listing_card`; mirror the allowlist in the route so the user gets a 400 instead of a raw constraint error. Have `MessageBubble` read the quote price from the commission row rather than attachment metadata, or have the accept route stamp the card's metadata from the row it just wrote.

### P3 — `commissions` has no INSERT guard, so a client can create a commission in any status for any artist

**Where:** `supabase/migrations/00001_initial_schema.sql:364-365` (INSERT policy `WITH CHECK (auth.uid() = requester_id)` and nothing else); `00009_rls_column_guards.sql:125-128` (removed the UPDATE policy on the assumption that "all mutations now go through ownership-checked, service-role API routes"); `src/app/api/commissions/route.ts:37-46` (the route's `is_live` gate and schema live only in the route); `src/app/api/admin/commissions/route.ts:20-32` and `src/app/api/cron/commission-nudges/route.ts:19-23` (readers that trust `status`).

**What happens:** A signed-in user POSTs to `/rest/v1/commissions` with `{requester_id: <self>, artist_id: <any artist, live or not>, title, description, status: "disputed", dispute_reason: "…"}`. The policy passes, every CHECK passes, and the row appears in the admin `/admin/commissions` disputed queue with no conversation behind it; an admin resolves it and both parties get a notification for a dispute that never happened. With `status: "in_progress"` and `quoted_price_cents` of the attacker's choosing, the row shows in the artist's Studio queue as work they never quoted, and after 14 days the nudge cron emails the artist to post progress on it. The route's 5/min bucket, its `is_live` check, and its zod schema are all bypassed.

**Why it's real:** 00030/00032 recognised exactly this class for `artist_profiles` and added `guard_artist_profiles_insert`; `commissions` got the UPDATE policy removed but no INSERT guard, and the comment in 00009 shows the assumption that routes are the only writers. The CHECK constraints (00001, 00048, 00053) bound the values but not who may set them. No money is attached to commissions (DECISIONS D5), which is why this is a P3 maintainability trap rather than a P2: the next feature that trusts `commissions.status` or `quoted_price_cents` as artist-written will be wrong.

**Fix direction:** Add `guard_commissions_insert` that, when not `is_privileged()`, forces `status = 'pending'` and nulls `quoted_price_cents`, `estimated_completion`, `artist_notes`, `closed_by`, `closed_reason`, `dispute_reason`, `pre_dispute_status`, `last_nudge_at`, and requires the target artist to be `is_live`. Pin it in the smoke test's function list.

## Not findings

- **First-pass fixes, re-read against callers.** `guard_profiles_update` (00052) freezes `email` and `unsubscribe_token`, and the UPDATE grant is column-level; `AuthContext` and the account page never write either. `follows` is own-row and `follower_count()` is the only public number; `/api/analytics` uses it. `is_privileged()` now names its trusted contexts; the service-role client presents `role: service_role`, GoTrue's cascades present no claims, and `guard_gallery_profile_update` delegates to it. The admin reset link goes to `/auth/reset-callback` with `hashed_token`, verifies with the cookie server client (a route handler, so cookies are writable), and `/reset-password` shows the expired state when it arrives session-less. `/api/account/delete` refuses on `paid|shipped|disputed` or an unsettled refund, as buyer or as the artist behind the order, and fails closed on a query error. `website_url` has the scheme CHECK on both tables. `analytics_events` has no client INSERT policy; `/api/analytics` POST inserts with the service role after zod. `verification_requests` and `reports` INSERT pin their review columns. None of these regressed.
- **Admin client enumeration (48 call sites, all read).** The eleven `admin/*` call sites and `galleries` PATCH follow `getUser()` then `profiles.role === 'admin'` (services uses a `requireAdmin` helper with the same check). `account/delete` reads and deletes only `user.id`. `artist/application`, `artist/submit`, `payments/stripe-connect` filter every read and write on `profile_id = user.id`. The seven `commissions/[id]/*` sites read the row under the caller's RLS, check requester or artist explicitly, then write with a compare-and-swap on id + status. `orders/approve-refund`, `confirm-pickup`, `mark-delivered`, `notify-shipped` check the caller is the order's artist or buyer before the write. `listings` POST and `listings/[id]` PATCH use it only to claim email stamps on a row already ownership-checked. `commissions` POST, `messages` POST, `reviews` POST read a counterparty's email after an RLS-guarded insert. `payments/checkout` reads the artist row for a listing the caller could already see. `analytics` POST is unauthenticated by design and throttled. `unsubscribe` is token-keyed. `webhooks/stripe` is signature-gated. The five cron routes compare `CRON_SECRET`. `listingAlerts.ts` is server-only and called from ownership-checked routes.
- **IDOR across `[id]` and `[slug]` routes.** Every writing route checks party membership, not existence: commissions (artist via `artist_profiles.profile_id`, requester via `requester_id`), orders (artist or buyer), listings (owner via embed), artists (owner), conversations/[id] GET (explicit participant check). `conversations/[id]/read` relies on the messages UPDATE policy, which is membership-scoped. Admin `[id]` routes are role-gated, which is the model.
- **Conversation membership.** I went looking for the participant-swap hole (UPDATE policy is `USING`-only, so either participant could satisfy it after reassigning the other column) and found `guard_conversations_update` (00031) freezing both participant columns for non-privileged callers. `context_id`/`context_type` stay writable on purpose and only reach RLS-guarded reads.
- **Storage routes.** Path is `${user.id}/${Date.now()}-${random}` chosen server-side (`signedUpload.ts:25`); the client never supplies it. Every bucket's INSERT policy is folder-scoped to `auth.uid()` after 00038. Content type is caller-declared on the PUT but the bucket's `allowed_mime_types` (00012) rejects anything outside JPEG/PNG/WebP, plus PDF for chat and video types for videos; size is capped per bucket (2 MB avatars, 5 MB images, 10 MB chat, 200 MB video). `chat-attachments` is private, its SELECT is uploader-folder or participant-via-attachment, and `MessageInput` stores the object path and renders through `createSignedUrl` under the caller's session. The listing gap above is the only issue.
- **Rate limiting coverage.** The matcher is `/api/:path*` minus `/api/webhooks` and `/api/cron`. Covered: message send (`/api/messages` 120/min per IP), review submit (`/api/reviews` 5/min POST, 60 GET), commission create (5/min), Stripe Connect (3/min), checkout (10/min), everything else 60/min. Not covered and not coverable here: signup, login, password reset, and confirmation resend, which go from the browser to Supabase Auth and are governed by GoTrue's own limits plus Turnstile (`captchaEnabled` is derived from `NEXT_PUBLIC_TURNSTILE_SITE_KEY`; whether GoTrue *enforces* the captcha is a dashboard setting I cannot see). Also not covered: direct PostgREST inserts into `messages`, `reviews`, `reports`, `commissions`, which the first pass already filed and the plan left as a per-table decision. `/auth/callback` and `/auth/reset-callback` are unthrottled but consume single-use, high-entropy tokens.
- **Auth callback and login redirects.** `isSafeInternalPath` rejects `//`, backslashes, whitespace and control characters; `/%2F%2F…`, `/@host`, and `/\t//` all stay on-origin or are refused. Both consumers use it; the reset callback redirects to fixed paths.
- **Email enumeration.** Signup returns a stub user with no session for an existing address and the page renders the same screen (under email confirmation; see appendix for the autoconfirm caveat); `resend` and `resetPasswordForEmail` are silent on unknown addresses; login shows one generic error for a wrong password.
- **Sign-out completeness.** `supabase.auth.signOut()` defaults to global scope; the Navbar now catches and toasts a failure (R5), and the account page signs out after the server confirms deletion. A JWT that outlives a deleted user fails `getUser()` on every route and `PGRST116` in `AuthContext`, so it grants nothing.
- **Signup role.** `handle_new_user` (00023) coerces anything but `artist`/`gallery` to `user`; `guard_profiles_update` blocks later changes; `guard_artist_profiles_insert` (00032) forces `draft`/`is_live=false` regardless of what the onboarding insert sends.
- **Stripe webhook.** Signature verified against both endpoint secrets with the SDK's 5-minute tolerance; the body is read as text before parsing. No event-id ledger, but every order-state handler is idempotent by state and compare-and-swap after R2 (`neq('status','disputed')`, `stripe_reversal_id` check, idempotency keys on every Stripe mutation). The one non-idempotent write is `account.updated` (appendix). Money-side ordering concerns are in `04-money-r2.md`.
- **NEXT_PUBLIC surface.** `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `APP_URL`, `PAYMENTS_ENABLED`, `SENTRY_DSN`, `TURNSTILE_SITE_KEY` are the only ones referenced in `src/`; all are public by nature. `SUPABASE_SERVICE_ROLE_KEY` is read only in `supabase-admin.ts`, imported only by route handlers and `lib/listingAlerts.ts`. `UPSTASH_*` and `CRON_SECRET` are read in middleware and route handlers, which are server bundles. `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is in the env example but unused.
- **RLS as the deny layer.** Tables whose policies allow a read the UI does not offer, for the record: `profiles` (`full_name`, `avatar_url`, `role`, timestamps to anon; ruling D3), `gallery_profiles` (all rows including unverified, with `address`, to anon; unchanged since pass one), `reviews` (`reviewer_id`, `order_id` UUIDs to anon), `artist_services` (contact details to every signed-in user, by design per 00034). Correctly private: `orders`, `commissions`, `commission_updates`, `messages`, `message_attachments`, `notifications`, `saved_listings`, `follows`, `blocked_users`, `muted_conversations`, `verification_requests`, `reports`, `analytics_events`, `drip_emails_sent` (no policy at all). `artist_profiles` and every child table follow `is_live`, and the column grants hide `stripe_account_id`, `rejection_reason`, `reviewed_*`, `email`, `unsubscribe_token`. The read RPCs from 00051 are `SECURITY INVOKER`; `follower_count`, `link_education_partners`, and `refresh_completeness_score` are `SECURITY DEFINER` but return a count, link rows by exact name match, or recompute a score, none of which leaks or elevates.
- **Reassigning ownership through UPDATE.** `listings`, `artist_profiles`, `gallery_profiles`, `profiles`, `notifications`, `conversations` (via the guard) all keep their owner column fixed: the policies are `USING`-only so Postgres applies the predicate to the new row, and the guards cover the rest.
- **`x-forwarded-for` in the limiter.** Vercel overwrites the header with the connecting IP, so the first entry is correct on this host.
