# Frontend quality — review 2026-09-02

**Files read:** every file under `src/components/**` (78 client files, 26 server-renderable), every page and layout under `src/app/(public)`, `src/app/(artist)`, `src/app/(user)`, and all four files in `src/context/`. For verification I also read `src/hooks/{useOrders,useListings,useArtistProfileId,useArtist,useArtistContent,usePartnerPicks,useFollows,useSaved,useFeed,toastError}.ts`, `src/services/{listings,orders,saved,follows}.ts`, `src/schemas/{listingSchema,artistSchema}.ts`, `src/lib/{queryClient,publicProfile}.ts`, `src/app/providers.tsx`, `src/app/globals.css`, `tailwind.config.ts`, `src/app/api/listings/[id]/route.ts`, `src/app/api/commissions/[id]/decline/route.ts`, `supabase/migrations/00033_listing_visibility_and_privacy.sql`, and the `handleSubmit` implementation in `node_modules/react-hook-form` 7.71.2.

Skipped: `src/components/upload/downscaleImage.ts` (pure canvas resize, no UI); the bodies of `(public)/terms`, `(public)/privacy`, and `(public)/artist-agreement` beyond their first 25 lines (static copy, server-rendered, no interaction). No e2e spec exercises keyboard or screen-reader behaviour, so every accessibility finding below is from code reading; contrast ratios were computed from the hex values in `tailwind.config.ts` with the WCAG 2.x formula.

**Verdict:** The write paths are in good shape: every client-side mutation I traced asserts rows or routes through a hook with `toastError`, destructive actions almost all confirm, and buttons disable while pending. The weak side is everything that is not a write: no dialog in the app manages focus, seven fetch-backed surfaces present a failure as "you have nothing", and two multi-step submit handlers have no error path at all.

### P1 — No dialog in the app moves, traps, or restores focus, and two lightboxes cannot be closed from the keyboard
**Where:** `src/components/ui/Modal.tsx:21-52` (used by 11 callers plus `ConfirmDialog.tsx:38`), `src/components/feed/FilterDrawer.tsx:14-27`, `src/components/artist/MeetTheArtist.tsx:65-84`, `src/components/commission/CommissionUpdates.tsx:120-124`
**What happens:** A keyboard user on Studio → Sales tabs to "Mark as Shipped" and presses Enter. The Ship Order modal renders into a portal at the end of `<body>`, but focus stays on the now-covered button. The next Tab moves through the rest of the Sales page behind the overlay; the Carrier select and Confirm Shipment button are reachable only after tabbing past every element on the page. A screen reader announces nothing when the dialog opens because it has no accessible name (no `aria-labelledby`, the title is a plain `<h2>`), and the close control is an unlabeled icon button that reads as "button". On close, focus is not restored, so it lands on `<body>`. The same applies to every `useConfirm()` dialog (remove artist, remove pick, approve refund, delete photo, block user), the delete-account modal, the location picker, and the report dialogs. `FilterDrawer` has no `role="dialog"` and no Escape handler. The `MeetTheArtist` and `CommissionUpdates` lightboxes have no Escape handler either, and the commission one has no close button at all: the only way out is a click on the backdrop.
**Why it's real:** A repo-wide grep of `src/components`, `src/app`, and `src/context` for `.focus(`, `autoFocus`, `inert`, `aria-labelledby`, or any focus-trap library returns zero hits. `ImageCarousel.tsx:97-104` is the one dialog with `role`, `aria-modal`, an `aria-label`, and Escape, but it too never moves focus into itself.
**Fix direction:** Give `Modal` an `aria-labelledby` pointing at its title, an `aria-label` on the close button, and on open move focus to the first focusable child and restore it to the opener on close, with Tab/Shift+Tab wrapped inside the panel. Route `FilterDrawer` and the two lightboxes through the same component or at minimum give them Escape and a labeled close button.

### P2 — A failure after the listing insert leaves Create Listing looking untouched, and pressing Publish again creates a second listing
**Where:** `src/app/(artist)/listings/new/page.tsx:63-93`, `src/app/(artist)/listings/[id]/edit/page.tsx:86-110`, `src/hooks/useListings.ts:15-27`, `src/services/listings.ts:53-91`
**What happens:** An artist on a flaky mobile connection presses Publish. `createListing` succeeds through the API route. The next call, `addListingImages` (a client-side `listing_images` insert), fails on a network blip or a storage-URL mismatch and throws. `onSubmit` has no try/catch, so react-hook-form rethrows it as an unhandled rejection; `isSubmitting` resets to false, no toast appears (the `toastError` on `useCreateListing` only wraps the create call), and `router.push` never runs. The artist sees the same filled-in form with the button back to normal, assumes the tap didn't register, and presses Publish again. A second listing row is created. The first one exists with no images and, if it was published rather than drafted, it is live in the feed with a "No image" card. On the edit page the same shape means a `setListingTags` failure after a successful PATCH shows nothing and stays on the page, so the artist cannot tell whether the price change saved.
**Why it's real:** `react-hook-form` 7.71.2 `handleSubmit` stores the thrown error as `onValidError` and rethrows it after resetting state (`dist/index.esm.mjs:2211-2229`). `addListingImages` and `setListingTags` both `throw error` (`services/listings.ts:60,71,89`). Neither page wraps `onSubmit` or passes an `onInvalid`. Compare `CommissionForm.tsx:41-66`, which wraps its fetch and toasts.
**Fix direction:** Wrap both `onSubmit` bodies in try/catch that toasts and, on the create page, remembers the created listing id so a retry patches images onto it instead of inserting again. Better still, have the `/api/listings` POST accept image URLs and tags so the create is one call.

### P2 — Seven fetch-backed surfaces render their empty state when the fetch fails
**Where:** `src/components/studio/SalesSection.tsx:31,52,108`; `src/app/(user)/orders/page.tsx:31,43,86`; `src/app/(user)/following/page.tsx:12-19`; `src/app/(user)/saved/page.tsx:11-18`; `src/components/studio/ListingsSection.tsx:18-33`; `src/components/studio/SeriesSection.tsx:22,97,108`; `src/components/gallery/PartnerPicksManager.tsx:34,136`; also `src/app/(artist)/studio/services/page.tsx:33-45`, `src/components/dashboard/GalleryDashboard.tsx:44-75`, `src/components/commission/CommissionPanel.tsx:34-44,117`
**What happens:** An artist opens Studio → Sales while their connection is degraded. `getOrdersByArtist` throws, React Query retries once (`queryClient.ts:11`) and gives up; `isLoading` goes false with `data` undefined. The component destructures only `data` and `isLoading`, so it renders "No sales yet — when collectors purchase your art, orders will appear here." The artist with a paid order awaiting shipment believes nothing sold. There is no retry control and no error text. The buyer's My Orders page, Following, Saved, the Work tab listings, Series, and Partner Picks all behave identically. `CommissionPanel` swallows the error inside `queryFn` and returns null, so a transient failure reads "Commission not found." `GalleryDashboard` on a `gallery_profiles` error falls through to render a dashboard for a null gallery showing a "Pending Review" badge and an Add Artist button whose search silently does nothing.
**Why it's real:** Every service function involved does `if (error) throw error` (`services/orders.ts:14,26`, `follows.ts:11`, `saved.ts:52`), so `isError` is set; none of the listed components reads it. `ArtFeed.tsx:125-126,161-162` shows the pattern done right, and `ArtistProfileEdit.tsx:117-130` even has a retry button, which proves the distinction was known.
**Fix direction:** Read `isError` in each of these and render a small error state with a retry (a `refetch` call) instead of the empty copy. For the hand-rolled fetches (services page, GalleryDashboard, CommissionPanel's queryFn), surface the error rather than coercing it to null.

### P2 — Submit for review spins forever on a network error, and a null auth read disables it forever
**Where:** `src/components/studio/SetupChecklist.tsx:35-52,118-134,179-186`
**What happens:** A draft artist taps "Submit for review" on a phone that drops the request. `fetch` rejects with a TypeError; `submit` has no try/catch, so `setSubmitting(false)` never runs. The button shows a spinner indefinitely with no toast, and the artist cannot retry without reloading. Separately, the avatar check calls `supabase.auth.getUser()` directly instead of the `useAuth()` context that every other component uses; if that call returns no user (a token-refresh race) the early `return` leaves `avatarLoaded` false, so the button stays disabled and the hint "To submit: profile photo, your story, and at least one listing" tells the artist to add a photo they already have.
**Why it's real:** `submit` is a bare `async` with an unguarded `await fetch(...)`. The `.then(success, failure)` on line 44-49 only covers the profiles query; the `if (!user) return` on line 38 has no failure branch. Compare `CommissionPanel.performAction` (`CommissionPanel.tsx:69-91`) which wraps the same fetch shape in try/catch/finally.
**Fix direction:** Wrap `submit` in try/catch/finally so `submitting` always resets and a toast names the failure. Read the user id from `useAuth()` and treat "no user" as loaded.

### P2 — Edit Listing renders any listing the session can read, including a deleted one as a blank editable form
**Where:** `src/app/(artist)/listings/[id]/edit/page.tsx:28,84,112-143`, `src/services/listings.ts:4-11`, `supabase/migrations/00033_listing_visibility_and_privacy.sql:11-21`
**What happens:** An artist follows a stale link to a listing they deleted. `getListingById` throws PGRST116, `isLoading` flips false, and the page renders "Edit Listing" over an empty form with a Save button; there is no not-found state and nothing tells them the listing is gone. If instead they paste another live artist's listing id, the RLS policy allows the read (public listings are visible to everyone), so the other artist's title, price, and images load into the editor with working Move/Remove buttons. Save returns 403 from the PATCH route and toasts "Forbidden"; Remove image returns zero rows and toasts. No data escapes and nothing is written, but the surface presents another artist's work as editable and offers no explanation for the refusal.
**Why it's real:** The page never checks `listing.artist_id` against the signed-in artist's id (which it has, in `artistId` from line 36-41) and never reads `isError`. The 00033 policy grants SELECT on any non-hidden, non-draft listing whose artist is live. The API route does check ownership (`api/listings/[id]/route.ts:29-37`), which is why this is P2 rather than P0.
**Fix direction:** After load, redirect or render a not-found state when the query errors or when `listing.artist_id !== artistId`. Keep the server check as the real guard.

### P2 — Primary buttons, brand-orange links, and both success/warning toasts fail AA text contrast
**Where:** `tailwind.config.ts` palette; `src/components/ui/Button.tsx:6`; `src/components/ui/Toast.tsx:20-23`; `src/components/ui/Badge.tsx:5,9`; `text-terra` link usages in `NeedsAttention.tsx:77`, `GalleryGrid.tsx:53`, `RelatedListings.tsx:42`, `(artist)/studio/page.tsx:56`, `FeedFilters.tsx:122`, `CookieConsent.tsx:25`
**What happens:** A low-vision buyer reads the listing page: the artist link and every price on the profile grid is `text-terra` on cream, and the "Buy Now" label is white on terra. After a save, the confirmation toast is white on sage; a warning toast is white on Tailwind yellow-500. Computed ratios against the configured hex values:

| Pair | Ratio | AA (4.5:1) |
|---|---|---|
| white on terra (primary Button, Sign Up, hero CTA) | 3.07 | fail |
| terra on cream (links, prices, eyebrows) | 2.85 | fail |
| terra on terraSoft (Connect now banner link) | 2.62 | fail |
| white on sage (success toast) | 3.63 | fail |
| sage on white / cream (success Badge, "Review submitted") | 3.63 / 3.37 | fail |
| white on yellow-500 (warning toast) | 1.92 | fail |
| muted on cream / white / sand (body secondary) | 4.98 / 5.36 / 4.41 | pass (sand fails) |
| ink on cream | 13.26 | pass |

Button text is `text-sm font-medium`, below the 18.66px bold "large text" threshold, so 3:1 does not apply.
**Why it's real:** Straight arithmetic on the palette. `terraDark` on cream is 3.9 and on white 4.2, so even the hover state does not reach AA. The `AccentPalette` comment claims swatches are "all dark enough for white text on CTAs"; the brand terracotta itself is not.
**Fix direction:** Move body-text and link uses of `terra` to a darker step (a `#B5502E`-range value clears 4.5 on cream) and reserve the bright terracotta for non-text accents and large display type. Restyle success and warning toasts with dark text on tinted backgrounds, which also fixes `Badge` success.

### P2 — The masonry feed reserves a 4:5 box for every image and reflows when the real ratio loads
**Where:** `src/components/feed/FeedCard.tsx:45-53`, `src/components/feed/ArtFeed.tsx:143-149`, `src/types/listing.ts:31-37`; also `src/components/feed/RecentlyViewed.tsx:14-54`
**What happens:** The home feed passes `natural` so each card shows the artwork at its own aspect ratio. `next/image` is given `width={600} height={750}` with `h-auto w-full`, so the browser lays out every card as 4:5 and then resizes it when the bytes arrive. A landscape painting shrinks to roughly half its reserved height; a tall piece grows. Because the grid is CSS `columns-2`, every resize re-balances items across columns, so cards visibly hop between columns as the page loads and again on each infinite-scroll page. On the same page, `RecentlyViewed` renders nothing until two sequential queries finish and then inserts a full shelf above the "Discover" heading, pushing the feed down after the buyer has started scrolling.
**Why it's real:** `ListingImage` stores only `image_url`, `display_order`, `is_primary`; no width or height exists to size the placeholder correctly, and `sizes` alone does not fix reserved height. `HomeShelves` deliberately pops in the spotlight and picks shelves, but comments there defend that for shelves that are usually empty; `RecentlyViewed` is non-empty for any active buyer.
**Fix direction:** Capture intrinsic width/height at upload (the `/api/storage/listing-image` path already receives the blob) and store them on `listing_images`, then pass the real dimensions to `next/image`. Give `RecentlyViewed` the same skeleton treatment as the Featured shelf.

### P2 — Declining a quote and cancelling a request are irreversible and have no confirmation, unlike every other destructive action
**Where:** `src/components/commission/CommissionPanel.tsx:208-232`, `src/components/chat/MessageBubble.tsx:73-108`, `src/app/api/commissions/[id]/decline/route.ts:43-53`
**What happens:** A requester opens the commission rail on a phone. "Accept Quote" and "Decline" are two `size="sm"` buttons side by side. A mis-tap on Decline fires `performAction('decline')` immediately; the route sets `status = 'cancelled'` with `closed_by = 'requester'` and the commission is closed. The artist is notified that the buyer declined. There is no confirm, no undo, and the route's status guard means it cannot be reopened. The same pair with the same behaviour is rendered inside the quote-card chat bubble. "Cancel Request" on a pending commission behaves the same way.
**Why it's real:** Every other terminal action in scope goes through `useConfirm()` or a modal: approve refund (`SalesSection.tsx:72-79`), remove artist, remove pick, delete listing, delete series, delete photo, block user. Artist-side Decline does get a form (`CommissionPanel.tsx:280-314`), so the asymmetry is on the requester side only.
**Fix direction:** Route requester Decline and Cancel Request through `useConfirm()` with `destructive: true`, on both the rail and the chat bubble.

### P2 — Profile-editor validation errors are announced only by a 4-second toast, and most fields never show them inline
**Where:** `src/components/profile/ArtistProfileEdit.tsx:221-242,259,292,338`, `src/schemas/artistSchema.ts:11,15,19`, `src/components/ui/Toast.tsx:35`
**What happens:** An artist types `myportfolio.com` into Website and taps Save at the bottom of a page that is eight fieldsets long. Zod rejects it (`z.string().url()` requires a scheme). The `onInvalid` handler toasts "Check the Website field — it needs fixing before this can save." at the top-right of the viewport and removes it after four seconds. The Website input receives no `error` prop, so nothing on the page is marked; the same is true for Graduation Year (rejects anything outside 1900–2030), Minimum Price (rejects negatives), and every textarea. If the artist looks down at the button while tapping, they see Save do nothing. Only Display Name and City pass `error=`.

The edit and new listing pages pass `error=` for their validated fields, so the omission is specific to this form.
**Fix direction:** Pass `errors.<field>?.message` to every registered `Input` and render the message under each textarea; on invalid submit, also `scrollIntoView` and focus the first errored control. Consider making error toasts persist until dismissed.

## Not findings

- Client writes assert rows per `docs/CONVENTIONS.md`: `ArtistProfileEdit` avatar/banner, `GalleryProfileEdit`, `AwayModeToggle`, `EmailPreferences` (with `withSessionRetry`), `GalleryDashboard.handleRemoveArtist`, account name save, `updateListingImage`/`deleteListingImage`, `unfollowArtist`. No bare `catch {}` around a write anywhere in scope.
- Every mutation hook used with `.mutate()` fire-and-forget (`useToggleSave`, `useToggleFollow`, `useCreateListing`, `useUpdateListing`, `useDeleteListing`) carries `toastError`; the ones without it (`useUpdatePinned`, `useAddPick`, `useRemovePick`, `useUpdatePick`, `useConfirmPickup`, `useSaveEducation`) are called with per-call `onError` or `mutateAsync` in try/catch at every site I found.
- `Button` disables itself while `loading`, so the Confirm Shipment, Approve refund, Submit report, Update Password, and Send Quote paths are protected against double submit.
- Delete Account requires typing DELETE, goes through a server route, and the button is disabled until the text matches.
- `ArtFeed` has loading, error, and both empty variants; `ArtistProfileEdit` distinguishes load error from not-found and offers retry.
- `ImageCarousel` handles arrow keys and Escape, labels every control, restores body overflow on unmount, and uses `priority` on the first image with a correct `sizes`.
- `next/image` usage elsewhere is correct: `fill` sites all carry `sizes` except `ProfileHero` banner (defaults to 100vw, which is right); fixed-size avatars and thumbnails do not need `sizes`.
- `LocationContext` wraps both `localStorage` reads and writes in try/catch and still sets `ready`.
- `AuthGuard` preserves the query string in `returnUrl`; `ArtistSetupGuard` fails open on error and never redirects on stale data.
- `PurchasePanel` branches for own listing, hidden price, away mode, and payments-disabled are mutually exclusive and each keeps the Message button; the fee line is a display of `calcSplit`, not a computation the server trusts.
- Edit Listing deliberately avoids react-hook-form's reactive `values` so background refetches cannot wipe edits or double-convert dimensions; `toCm` round-trip preserves stored precision.
- Listing PATCH and DELETE ownership is enforced in the API route; the commission decline route re-checks status with a conditional update.
