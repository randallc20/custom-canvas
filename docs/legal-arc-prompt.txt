## Environment facts, all of which cost real time when forgotten

- node is not on PATH. Start every shell command with: export PATH=$HOME/.nvm/versions/node/v24.16.0/bin:$PATH
- Never run pnpm in this repo. Use ./node_modules/.bin/* directly. npm is the package manager.
- Work in a git worktree per phase, branch named legal/l1-publish-documents and so on. Symlink node_modules from the main tree and copy .env.local into each worktree; do not npm install in a worktree.
- There is no migration history table. Migrations are plain SQL applied by hand with psql, DEV first, prod only in section D. DEV connection: host aws-1-us-east-2.pooler.supabase.com, user postgres.nlatruygmarojthfjzog, password from SUPABASE_DB_PASSWORD in .env.local. Never touch anything named PROD_* until section D. Migration numbers start at 00058 and the plan assigns them per phase; if you run phases in parallel, assign each one its own number up front so two branches never collide.
- Every migration ships with its scripts/db-smoke.sql expectations in the same commit. Run ./scripts/db-smoke.sh after applying.
- Staging is custom-canvas-chi.vercel.app and auto-deploys on push to master. Production is customcanvas.shop and deploys only by hand with: npx -y vercel@59.5.0 deploy --prod --yes — no --token, the CLI is logged in on this machine.
- The e2e suite runs against staging with ./scripts/run-e2e.sh, one spec file at a time, workers=1, with a pause between files. Supabase auth throttles concurrent logins: do not run any other browser login, agent or script against DEV while the suite is running, or you will get a wave of false failures that all look like "stuck on /login".
- After pushing, staging takes a couple of minutes to serve the new build. Wait for it before running e2e, or you will test the old code. Fingerprint the build by hashing the /_next/static script URLs on the homepage and waiting for that hash to change.
- Two files reliably conflict when phases run in parallel: scripts/db-smoke.sql and DECISIONS.md. Resolve by keeping both sides.

## The operating loop, which is the part that actually produces the quality

**Per phase.** Read the cited documents. Build. Then the full verification bar: tsc --noEmit, next lint, vitest run, next build, and db-smoke if the phase has a migration — plus the phase's own Accept checks from the plan. A phase is not done until all of those are green. Include next build every time; a change that type-checks can still fail the production build, and that happened in the last arc.

**Per merge.** Merge to master, then run the bar again on the merge result. Merges introduce defects that neither branch had; that also happened in the last arc, twice. Only then push.

**Per group of phases.** Once staging is serving the new build, run the full e2e suite with E2E_MONEY=1. Fix every failure before moving on, and be precise about which kind each one is: a real product regression, or a test whose selector or assumption went stale because the product legitimately changed. Both need fixing. Only one is a defect. In the last arc a palette rename, a new confirmation dialog and a repositioned toast each broke a spec, and one of those three, the toast covering the account menu, was a genuine product bug that only surfaced because the suite ran.

**Per arc, and this is the step people skip.** Run a fresh review pass over what changed, in a separate headless session so it reads the code cold. Fix what it finds. Then run the pass again. Keep going until a pass comes back with no P0 and no P1 findings. In the last arc the money slice took four passes: each one found less than the last, and the fourth being clean was the gate to deploy. Do not treat "I fixed the findings" as finished. Treat "a fresh pass found nothing serious" as finished.

The prompts for those passes are in docs/reviews/prompts/. For this arc use pass-4-money.txt over the refund, cancellation and return changes, and pass-1-auth-access.txt over the acceptance, versioning and DMCA work. Edit the report path in the prompt so each run writes a new file rather than overwriting the last one. Run them with the Claude Code binary headless, from the repo directory, detached so a long run is not killed:

nohup ~/.vscode/extensions/anthropic.claude-code-*/resources/native-binary/claude -p --model claude-opus-5 --dangerously-skip-permissions --output-format text "$(cat docs/reviews/prompts/pass-4-money.txt)" < /dev/null > /tmp/pass.log 2>&1 &

Each pass takes ten to twenty minutes.
